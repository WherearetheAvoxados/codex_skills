# 제출 전 마무리

구현 중 단계별 검증 · 실패 처리는 $follow-plan이 맡는다. 이 스킬은 마지막에 한 번, 제출할 상태를 만든다.

## 지키는 것
- 새 기능을 넣지 않는다. 고칠 것이 보이면 목록으로 보고하고 내가 고를 때만 고친다(고칠 때는 $follow-plan 규칙대로).
- 확인하지 않은 동작을 "된다"고 쓰지 않는다. 기준을 몰래 낮추지 않는다.
- 남은 시간이 알려져 있으면 그 안에 끝나게 순서를 줄인다: 1 → 2 → 5 → 4 → 3.

## 1. 지금 상태 점검
- `git status --short`로 바뀐 파일을 본다. PLAN.md의 상태 표와 실제 코드가 맞는지 본다.
- 앱 · 스크립트를 실제로 한 번 돌린다 (PLAN.md의 마지막 검증 명령, 또는 SOLUTION.md에 쓸 실행 명령).
- 에러 · 경고가 나면 핵심 줄과 위치만 보고하고 멈춘다.

## 2. SPEC 성공 기준 점검
SPEC.md의 성공 기준을 하나씩 실제로 확인한다.

| 성공 기준 | 확인 방법 (명령 / 화면) | 결과 |
|---|---|---|
| 기준 1 | `python app.py` → 표에 지점 5개 | ✓ / ✗ (이유) |

- 화면이 결과물이면 무엇이 보여야 하는지 적고, 내가 스크린샷으로 확인할 지점을 말한다.
- ✗가 있으면 남은 시간에 맞춰 무엇을 할지(고칠지, 한계로 적을지) 나에게 묻는다.

## 3. 정리
- 쓰지 않는 코드 · 파일 · 디버그 출력 · 임시 데이터를 지운다 (지우기 전 목록을 보여 준다).
- 깨끗한 상태에서 SOLUTION.md의 실행 방법을 처음부터 그대로 따라 해 본다.

## 4. DECISIONS.md 정리
- 한 줄 형식 유지: `결정 / 이유 / 버린 대안 / 출처(AI 제안 · AI 제안 수정 · 내 결정)`. 중복은 합치고, 뒤집힌 결정은 최종 것만 남기되 "바꾼 이유"를 붙인다.
- 출처가 빈 줄은 대화 · 기록으로 채우고, 모르면 나에게 묻는다(추측으로 "내 결정"이라 쓰지 않는다).
- 내가 AI 제안을 고치거나 거절했는데 줄이 없으면 지금 만든다: 버린 대안에 AI가 제안한 것, 이유에 내가 무엇을 왜 바꿨는지.
- 각 줄이 "왜?"에 SPEC 근거나 실행 결과로 답하는지 본다. 답 못 하는 줄은 나에게 묻는다.
- 사후 서술형 대비: 가장 중요한 결정 3개를 골라 내가 5분 안에 손으로 쓸 수 있는지 함께 본다.

## 5. SOLUTION.md (제출 문서 · README.md는 과제 원문이라 고치지 않는다)
```markdown
# (과제 이름)
## 무엇을 하나 (2~3줄, SPEC 목표)
## 실행 방법 (복사해서 바로 되는 명령)
## 구조 (`![구조도](docs/architecture.svg)` 한 줄: 왼쪽 구조, 오른쪽 단계 표)
## 주요 결정 (DECISIONS.md에서 3~5개: 결정 · 이유 · 버린 대안 · 출처)
## 한계 · 하지 않은 것 (SPEC 범위 밖 + 시간 부족으로 못 한 것)
## 확인한 것 (2의 성공 기준 점검표)
```
- 사실만 쓴다. 담당자에게 확인 못 한 가정은 "한계"에 적는다.
- "주요 결정"에는 출처가 **AI 제안 수정 · 내 결정인 것을 2개 이상** 넣고 줄 앞에 **[내 판단]**을 붙인다. 그 줄은 AI가 뭐라고 했고 내가 무엇을 왜 바꿨는지(내 결정이면 왜 그렇게 정했는지)까지 쓴다. 2개가 안 되면 지어내지 말고 그렇다고 나에게 말한다.

## 6. 보고 (짧게)
- 성공 기준 점검표, 남은 한계, 제출 전에 내가 직접 볼 것(스크린샷 지점, 실행 명령).
- 커밋은 요청받을 때만. push는 하지 않는다.
