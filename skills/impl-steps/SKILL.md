# 구현 단계 표 만들기 · 갱신

## 1. 찾기와 읽기
- PLAN.md의 단계 표를 찾는다. 없으면 SPEC.md의 성공 기준에서 단계를 뽑아 새로 만든다: 끝에서 끝까지 가장 얇게 도는 것 먼저, 단계마다 검증 명령과 기대 결과, SPEC에 없는 것은 "제안만".
- 진행 근거: 실행 결과(명령과 숫자), `git log --oneline -10`, 지금 대화. **근거 없이 "완료"로 바꾸지 않는다.**

## 2. 표 형식
```markdown
## 구현 단계 (MM-DD HH:MM 기준)
| # | 단계 | 검증 (명령 → 기대) | 결과 | 상태 |
|---|---|---|---|---|
| 1 | 최소 동작: 화면까지 | `python app.py` → 표 1개 | 표 1개 뜸 | ✅ 완료 |
|   | ① 하위 단계 | ... | ... | 🟡 진행 중 |
| 2 | 실제 데이터 | `pytest -q` → 3 passed | | 🔴 다음 |
| 3 | (시간 남으면) 정렬 | | | ⚪ 미착수 |
| - | 계획 밖: 엑셀 내보내기 | | | ⚪ 제안만 |
```
- 상태는 다섯 가지만: ✅ 완료 · 🟡 진행 중 · 🔴 다음 · ⚪ 미착수 · ⚪ 보류/없앰/제안만 (글자로 구분).
- **🔴 다음은 한 번에 하나.** 끝나면 ✅로 바꾸고 다음 줄로 옮긴다.
- 하위 단계(①②…)는 번호 칸을 비운다.
- 결과 칸에는 실제로 본 숫자 · 출력 한 줄. 핵심 숫자가 있으면 단계 이름 뒤에도 붙인다 (예: "② 응답 0.3초 ✓").
- 계획에 없던 일은 맨 아래 번호 "-"로. 요구사항에 없는 것은 "제안만"으로 두고 구현하지 않는다.

## 3. 고칠 때
- 줄을 더하거나 빼도 번호가 꼬이지 않게 맞춘다.
- 제목의 "기준" 시각을 지금으로 고친다.
- 구조도(arch-diagram)의 상태 색과 표의 상태가 어긋나면 함께 맞추자고 말한다.
- 계획 자체가 바뀌었으면(단계 추가 · 삭제) DECISIONS.md에 `바꿈: X / 이유 / 버린 대안` 한 줄.

## 4. 확인
- 표가 깨지지 않았는지(칸 수) 다시 읽는다.
- 바뀐 줄을 짧게 보고한다: 무엇이 ✅가 됐고, 무엇이 🔴 다음인지, 남은 시간에 들어가는지.
