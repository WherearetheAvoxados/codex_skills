# 요구사항 인터뷰 → SPEC.md

## 지키는 것
- 이 스킬 동안 코드를 쓰지 않는다. 만드는 파일은 SPEC.md 하나.
- 질문은 내가 담당자에게 직접 묻는다. 너는 질문을 제안하고, 내가 붙여 넣은 답을 정리한다.
- 한 번에 질문 3개 이내. 앞 답을 보고 다음 질문을 고른다.
- 답을 추측으로 채우지 않는다. 모르는 것은 "미확인"에 둔다.

## 1. 먼저 읽기 (짧게)
- README(과제 원문, 읽기만), 주어진 데이터 · 코드 폴더 구조만 훑는다(파일 목록, 데이터 첫 몇 줄).
- 읽은 것으로 이미 답이 나오는 질문은 묻지 않는다.

## 2. 질문 순서 (사소한 것 → 깊은 것)
| 단계 | 알아낼 것 | 질문 예 |
|---|---|---|
| ① 지금 업무 방식 | 지금은 누가 어떻게 하나 | "지금은 이 일을 어떻게 처리하고 계세요?" |
| ② 문제 사례 | 가장 불편했던 실제 한 건 | "최근에 가장 곤란했던 경우 하나만 들려주세요." |
| ③ 데이터 | 입력의 형식 · 양 · 품질, 어디서 오나 | "이 파일은 매번 같은 형식인가요? 빠진 값은 어떻게 하나요?" |
| ④ 결과 사용자 | 누가 결과를 어디서 보고 무엇을 결정하나 | "결과는 누가 보고, 보고 나서 무엇을 하시나요?" |
| ⑤ 성공 기준 | 무엇이 되면 성공인가 (숫자 · 화면) | "어떤 상태면 '이거면 됐다'고 하시겠어요?" |
| ⑥ 범위 밖 · 우선순위 | 이번에 안 해도 되는 것, 시간이 모자라면 먼저 할 것 | "시간이 부족하면 무엇부터 보여 드리면 될까요?" |

- 답이 모호하면 같은 단계에서 "예를 들면?"으로 한 번 더 파고든 뒤 넘어간다.
- 성공 기준은 확인할 수 있는 말로 바꿔 되묻는다. 예: "빠르게" → "1초 안에 화면에 뜨면 될까요?"
- 3시간 과제라면 ①~⑥을 질문 6~10개 안에 끝낸다.

## 3. SPEC.md 쓰기
```markdown
# SPEC
## 목표
- (한 문장: 누가, 무엇을, 왜)
## 성공 기준 (확인 방법과 함께)
- [ ] 기준 — 확인: 실행 명령 / 화면 / 숫자
## 범위 밖
- 이번에 하지 않는 것 (담당자 답 근거)
## 우선순위
1. 시간이 모자라면 이것부터
## 미확인 사항
- 아직 모르는 것 — 내가 정한 가정 (나중에 담당자에게 확인)
## 근거
- 질문 → 답 요약 한 줄씩
```
- 성공 기준마다 확인 방법을 붙인다. 붙일 수 없으면 기준을 다시 묻는다.
- 가정은 "미확인"에 적고 DECISIONS.md에도 `가정 / 이유 / 다른 가능성 / 출처` 한 줄로 남긴다.

## 4. 끝내기
- SPEC.md를 보여 주고 "빠진 것 · 틀린 것"을 묻는다.
- 내가 확정하면 끝. 계획 · 구현은 내가 따로 부른다($impl-steps, $follow-plan). 스스로 시작하지 않는다.
